# ADR 0006：写操作的边界，以及为什么预约提交是唯一例外

- 状态：已接受并经一次修订（初版 2026-09，2026-10-18 修订，2026-11-06 追溯整理）
- 相关：`desktop/internal/ui/booking.go`、`desktop/internal/ui/booking_test.go`、`docs/STATUS.md` F23

## 背景

学校业务里既有查询也有写操作。自动签到、自动选课、抢位、代抢涉及学术诚信与机会公平；代提交预约会真实占用公共场地。做工具的人很容易顺手把这些「自动化」当成卖点，但出问题时承担后果的是用户。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 把学校能做的自动化都做上（签到、选课、抢位、代提交） | 涉及学术诚信与机会公平，出问题时承担后果的是用户；这不是技术难度问题 |
| 一律不做写操作，只留只读查询与官方页面入口 | 最安全，但用户要在两个界面之间来回抄信息。初版确实这么选过 |
| **默认只读，只允许一类经用户逐步确认的写** | 选中（2026-10-18 修订后的形态） |

## 决定

### 初版（2026-09）

只做读取。不移植任何自动签到、自动选课、自动提交预约；预约模块一度删掉全部写端点，只留场地与空位查询，办理入口交给学校原页面。

### 2026-10-18 修订

按维护者决定，预约提交作为**唯一例外**恢复，但必须满足下列约束。`docs/STATUS.md` 的 F23 记录了这次边界变更——边界不是一句口号，改变时要有记录、有确认机制。

### 现在的边界

不做的，明确不做：自动签到、自动选课、抢位代抢、论文全文批量下载、任何无用户确认的后台写操作。

做的唯一一类写操作是预约提交，且是两步式：

1. `prepare` 只核对、不提交：重新读一次空位，生成两分钟有效的一次性 token；
2. 用户在界面上看到核对结果后明确确认；
3. `commit` 拿 token 再校验一遍才真正发出去。

这样「看到空位」和「点提交」之间如果位子被别人占走，会被拦下来，而不是替用户占一个不存在的位子。写操作用的登录态只放内存，进程结束即失效，不进存档、不落盘。

## 代价与边界

- 多一组写端点和一段状态机，要防重放、过期、越权、无登录态提交；每次改动都得补测试。
- 写操作必须用真实账号、真实场地验收，模拟响应不算通过；为避免为测试占用公共场地，这一项长期标「待验收」而不是硬跑一遍。
- README 里「预约只保留只读／只打开原页面」是初版的旧句，2026-11-06 已同步修正，避免文档与代码打架。CHANGELOG 保留当时的历史记录，**不回改**；边界变更以 `docs/STATUS.md` 的 F23 为准。历史日志描述的是那一刻的状态，把它改得像从未变过反而会丢掉判断的轨迹。

## 怎么验证

`booking_test.go` 断言：`GET prepare` 返回 405、没有 token 的 `commit` 返回 409、无登录态时 `prepare` 直接拒绝而不是先替用户去学校试一次；`README.md` 的功能边界段与路由表一致；发版说明里如实写「提交预约尚未用真实账号验收」。
