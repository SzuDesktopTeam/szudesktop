# ADR 0007：多窗口同时写，用修订号乐观锁加跨进程文件锁

- 状态：已接受（2026-09 起实施，2026-11-06 追溯整理）；平台语义差异是**已知待修项**
- 相关：`desktop/internal/ui/workspace.go`、`desktop/internal/ui/notebook.go`、`workspace_lock_windows.go`、`workspace_lock_other.go`

## 背景

应用会开多个窗口（主窗、宠物窗、独立笔记窗），也可能被启动两次。几个窗口同时保存笔记或庭院存档时，最怕的是「后写的悄悄覆盖先写的」，用户几天后才发现内容丢了。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只靠进程内 mutex | 挡不住第二个进程；单实例复用后也挡不住同进程内不同存档路径的并发 |
| 最后写入者胜 | 实现最省事，但静默丢数据，是这类工具最不能犯的错 |
| **修订号乐观锁 + 跨进程文件锁** | 选中：冲突时明确报错，让用户自己决定，数据不丢 |

## 决定

两层保护：

- **跨进程文件锁**：`lockWorkspace` 在写路径上加排他锁，Windows 用 `LockFileEx`（`workspace_lock_windows.go`），其他平台用 `flock`（`workspace_lock_other.go`）。
- **修订号乐观锁**：每次保存携带 `revision`；与当前值不一致返回 409 并提示「请先导出当前内容，再重新载入」，**不覆盖**；修订号到上限也返回 409，原文件保留。
- 存档损坏时恢复到上一次成功保存的版本，并把恢复事件显式告诉用户，不静默清空。
- 拿不到锁返回 503 并提示稍后重试——这是「忙」的信号，不是冲突结论，界面不能把它显示成「保存失败，内容已丢」。

## 代价与边界

- 写路径变长：每个保存都要拿锁、读当前修订号、比较、再写；大存档下比「直接覆盖」慢。
- 409 对普通用户是句硬话，界面必须说清「你的内容没丢，先导出再重载」，否则会被当成程序坏了。
- 乐观锁只解决「两个窗口改同一份存档」，不做多人实时协作，也不做变更合并；这跟 ADR 0004 的「数据只在本机」是一致的。
- 平台差异要靠测试矩阵兜，不能只在一个平台上宣布通过。

## 已知差异（未修，别当成设计）

两个并发写入用例（笔记、庭院各一）在本机 Windows 稳定返回 503（锁获取失败），而非 Windows 的 CI runner 返回 409（修订号冲突）。两边锁实现的行为不一致，语义没有统一；**这不是「Windows 就该这样」，是待修项**。同一时间窗口内没有改动过业务 Go 代码，CI 的 `test` / `test-macos` 与发布流水线的 Windows 构建都能通过，说明是本机环境与平台组合的差异，但结论仍是「要补测试矩阵并统一语义」，不能靠一句「环境不同」结案。

## 怎么验证

`notebook_test.go`、`workspace_test.go` 覆盖并发写入、修订号上限、损坏恢复；`go test ./desktop/internal/ui`；CI 的 `test` / `test-macos` 与发布流水线 `build-desktop-windows`。修掉上述差异时，应让两个平台对同一场景返回同一语义，并补一张平台 × 场景的测试矩阵。
