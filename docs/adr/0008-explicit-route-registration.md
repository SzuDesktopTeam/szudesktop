# ADR 0008：路由显式逐条注册，让安全断言能扫源码

- 状态：已接受（2026-09 起实施，2026-11-06 加强并追溯整理）
- 相关：`desktop/internal/ui/api_routes.go`、`desktop/internal/ui/api_token_test.go`、`desktop/internal/ui/api_guard.go`

## 背景

引擎有 69 条 `/api`，除健康检查等极少数公开接口外，每一条都必须经过 `protectAPI` 校验凭据（ADR 0002）。加新接口时最容易出的错不是写错业务逻辑，而是**忘了包那一层**——功能自己测得通，安全洞悄悄留下。

## 备选方案

| 方案 | 好处 | 为什么不选 |
|---|---|---|
| 用中间件统一包住整个 mux | 运行时一定安全，代码最省 | 源码上「哪条接口该公开」看不出来；漏配的公开路径只能靠运行时抓，静态检查帮不上忙 |
| 表驱动：一张路由表循环注册 | 行数少、看着清爽 | 断言要改成运行时遍历，且方法白名单、公开例外散在表里；改动时容易顺手把某条改成裸注册而没人发现 |
| **逐条 `mux.HandleFunc` + 源码扫描断言** | 每条的鉴权与方法白名单一眼可见，漏了会直接让单元测试变红 | 行数多，加接口必须写完整 |

## 决定

每条路由都写成 `s.protectAPI(s.handleX, http.MethodGet, ...)` 这种完整形式，公开接口走 `publicAPI` 并集中在白名单里。`api_token_test.go` 用正则**扫描包内所有生产 Go 文件**的路由注册，逐条断言：路径以 `/api` 开头时必须经过 `protectAPI`，且带显式方法白名单；公开路径必须在允许清单里。

2026-11-06 把 69 条路由从 `server.go` 拆到 `api_routes.go` 时，同时把断言的扫描范围从「只读 `server.go`」扩到「扫整个包的生产 Go 文件」。这一步是拆分的前提：否则文件一搬，安全断言会因为找不到源码而假绿。

## 代价与边界

- 新增接口必须写完整那一行，不能图省事用循环批量注册；路由表按业务域分组注释，保持可读。
- 断言依赖源码书写形式，属于「把约定写进测试」；好处是漏一层立刻红，代价是重构注册写法时要同步改断言。
- 静态断言只保证「包了 `protectAPI`」，不保证 handler 内部没有越权；业务层的会话与权限检查仍要靠各自的测试。

## 怎么验证

`go test ./desktop/internal/ui -run TestEveryAPIRouteRequiresCallerToken`；负向验证：临时写一条不带 `protectAPI` 的 `/api` 注册，测试必须变红，再恢复；`go test ./...` 与发布流水线的 `build-desktop-windows` 全绿。
